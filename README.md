# NaNDA Usage Metrics

The National Neighborhood Data Archive (NaNDA) publishes contextual data on US neighborhoods — pollution, parks, schools, transit, demographics, and more. This repository tracks who's actually using each dataset: monthly download counts, related publications, unique institutions, and historical trends, pulled from ICPSR and openICPSR.

**Live dashboard:** [the-national-neighborhood-data-archive.github.io/usage-metrics](https://the-national-neighborhood-data-archive.github.io/usage-metrics/)

Terms (`status`, `scrape_status`, `archive`, `deposit_via`, curated, self-published) are defined in [VOCABULARY.md](VOCABULARY.md).

## What's in this repo

A Python scraper (`nanda_usage_scraper.py`) runs monthly via GitHub Actions, hitting ICPSR's PCMS APIs for every dataset listed in `inventory.csv`. It produces a monthly snapshot CSV, a long-format monthly time-series CSV, a running download history rebuilt from every saved scrape, a Markdown delta report comparing the latest run to the previous one, and a self-contained HTML dashboard. `inventory.csv` lists what gets tracked. It is generated weekly from the private `nanda-inventory` repo's `deposit_status.csv`, where the dataset list is kept; see "Maintaining the inventory".

## Outputs

All under `data/` unless noted:

- **Monthly snapshot** — `nanda_usage_stats_YYYY-MM-DD.csv` (dated) and `nanda_usage_stats_latest.csv` (always overwritten). One row per dataset.
- **Time-series:** `nanda_usage_timeseries_*.csv`. Long-format monthly buckets per curated dataset, covering only the window ICPSR currently serves (roughly the past three years).
- **Download history:** `nanda_download_history.csv`. One running month-by-month history per curated dataset, rebuilt after every scrape from all the dated time-series files. It keeps months ICPSR has since dropped, and the dashboard takes its curated download totals and trend chart from it. Generated by `build_history.py`; don't hand-edit it.
- **Delta report** — `delta_*.md`. Plain-English summary of what changed since the last snapshot: total downloads, biggest movers, suspicious zeros, newly tracked datasets.
- **Dashboard**: `docs/index.html`. KPI cards, an aggregate monthly downloads chart, and a sortable table of every dataset. Published via GitHub Pages. Each row's title, version, DOI, and URL come from `inventory.csv` at build time, not from the snapshot, so a correction in the dataset list shows at the next build; the snapshot's values are used only for a study the inventory does not list. The dashboard is rebuilt whenever `inventory.csv` changes on `main` (`.github/workflows/build-dashboard.yml`, build steps only, no scrape) and after every monthly scrape.

## CSV schema

### Monthly snapshot (`nanda_usage_stats_*.csv`)

| Column | Description |
|--------|-------------|
| `study_id` | ICPSR or openICPSR study/project ID |
| `dataset_title` | Full dataset title (joined from `inventory.csv` by `study_id`) |
| `doi` | Dataset DOI (joined from `inventory.csv` by `study_id`) |
| `url` | Landing-page URL (joined from `inventory.csv` by `study_id`) |
| `total_downloads` | Total downloads (data + docs for curated; for openICPSR, `earlier_version_downloads` + `current_deposit_downloads`) |
| `total_views` | Total project-page views (openICPSR only, from the openICPSR usage endpoint; blank for curated) |
| `publications` | Count of related publications (curated ICPSR only; blank for openICPSR) |
| `data_downloads` | Data file downloads (curated, and openICPSR rows from the self-deposit usage source; blank in snapshots before 2026-12 for openICPSR) |
| `documentation_downloads` | Documentation file downloads (same coverage as `data_downloads`) |
| `unique_users` | Distinct users who downloaded (curated only; blank for openICPSR) |
| `num_institutions` | Distinct institutions that downloaded (curated only; blank for openICPSR) |
| `earlier_version_downloads` | openICPSR rows only, since the 2026-12 snapshot: downloads of the earlier version of the dataset, from the openICPSR usage endpoint. Blank for curated rows and in older snapshots |
| `current_deposit_downloads` | openICPSR rows only, since the 2026-12 snapshot: downloads of the current deposit, from the usage-statistics endpoint of ICPSR's self-deposit system. Blank for curated rows and in older snapshots |
| `scrape_status` | `success` or `error` — did this row's scrape work (snapshots dated before 2026-08 call this column `status`) |
| `error_message` | Populated when `scrape_status == error`, or for non-fatal sub-fetch failures (e.g., publications fetch error, unknown archive value, a usage source that failed and whose prior value was kept) |
| `timestamp` | When this row was scraped |

### Time-series (`nanda_usage_timeseries_*.csv`)

Long-format with one row per `(study_id, year, month)`. Months with zero activity are omitted. Curated ICPSR datasets only — PCMS doesn't expose a per-month feed for openICPSR.

| Column | Description |
|--------|-------------|
| `study_id` | ICPSR study ID (curated only) |
| `year` | Year of activity (e.g., 2024) |
| `month` | Month 1–12 |
| `data_downloads` | Data file downloads that month |
| `documentation_downloads` | Documentation downloads that month |
| `total_downloads` | Sum of the two |
| `timestamp` | When this snapshot was scraped (same value for every row in a run) |

### Download history (`nanda_download_history.csv`)

Long-format with one row per `(study_id, year, month)`, built by `build_history.py` from every dated time-series file (never `_latest`). When several snapshots contain the same month, the newest snapshot wins, because a later scrape is the better measurement of a month ICPSR still serves (it supersedes partial-month counts from mid-month runs). A month ICPSR no longer serves keeps the value from the last snapshot that had it. Curated ICPSR datasets only; sorted by `study_id`, `year`, `month`.

| Column | Description |
|--------|-------------|
| `study_id` | ICPSR study ID (curated only) |
| `year` | Year of activity (e.g., 2024) |
| `month` | Month 1–12 |
| `data_downloads` | Data file downloads that month |
| `documentation_downloads` | Documentation downloads that month |
| `total_downloads` | Sum of the two |
| `source_snapshot` | Date (`YYYY-MM-DD`) of the dated time-series file this row's counts come from: the newest one that contains this month |
| `in_latest_snapshot` | `True` if the newest snapshot still contains this month. `False` means the month survives only in this history, usually because ICPSR has dropped it (it can also mean the latest scrape missed that study) |

## How it works

Routing goes by `archive` first. Self-published rows ask two usage sources and add them; curated rows pick one source by `deposit_via`.

- **`archive=openICPSR`** (self-published, published or unpublished, whatever `deposit_via` says): two requests per dataset.
  - `pcms.icpsr.umich.edu/pcms/metrics/data/api/openicpsr/projects/{id}/usage/view?level=project`: total downloads and total views of the earlier version of the dataset on openICPSR. Saved as `earlier_version_downloads` and `total_views`.
  - `www.icpsr.umich.edu/sites/api/usage-statistics-api/usage-statistics/products/{id}`: GA4-backed downloads of the current deposit in ICPSR's self-deposit system, with a data/documentation split. Saved as `current_deposit_downloads`, `data_downloads`, `documentation_downloads`.
  - `total_downloads` is the sum of the two. ICPSR moved every NaNDA openICPSR deposit into its self-deposit system in 2026, after which the openICPSR endpoint mostly stopped counting while the new endpoint started from the move. A small number of downloads may be counted by both; ICPSR has not said.
  - If one source fails for a row, that source's value is reused from the most recent prior snapshot that has it and `error_message` says so, so a failed request never lowers a total. For an unpublished row, the self-deposit source not knowing the deposit (404, 500, or an empty body) is normal: `current_deposit_downloads` is 0 and nothing is logged.
- **`archive=ICPSR` + `deposit_via=RDE`** (curated studies ICPSR has moved onto RDE): `www.icpsr.umich.edu/sites/api/usage-statistics-api/usage-statistics/products/{id}` only. GA4-backed lifetime totals plus a data/documentation download split. No views, no publications, no time-series.
- **`archive=ICPSR` + `deposit_via=legacy`** (curated): `pcms.icpsr.umich.edu/pcms/metrics/data/api/downloadCount`, `/downloadInfo`, `/institution`: full breakdown of data vs. documentation downloads, unique users, and institutions.
- **Publications** (curated only): `www.icpsr.umich.edu/sites/api/solr/biblio/query_dm?q=STUDYQ:{id}&fq=STATUS:approved`, the Solr endpoint the public "Related publications" page uses; we read `response.numFound` for the count.

The first snapshot with the two per-source columns adds downloads that earlier snapshots never counted. For that one build, the dashboard and the delta report say how many downloads across how many datasets were newly counted.

Dataset titles are read from `inventory.csv` at startup, not fetched live. `cloudscraper` handles `pcms.icpsr.umich.edu`'s Cloudflare challenge.

**Download history.** ICPSR keeps a rolling three-year window of download history and trims its oldest months in batches, so the totals it reports shrink at every trim. After each scrape, `build_history.py` combines every dated time-series file into `data/nanda_download_history.csv`, which keeps each month's last saved value. The dashboard takes curated download totals, their month-over-month change, and the trend chart from that history; datasets without a monthly history (openICPSR, RDE, and any curated study PCMS serves no monthly buckets for) keep their reported totals. Unique users can't be rebuilt this way, because distinct users don't add up across months, so the dashboard labels them "past 3 years". The delta report stays on ICPSR-reported numbers, since it is the diagnostic that catches trims, plus one line giving the dashboard's total so the two reconcile.

**Never prune the dated snapshot files** (`nanda_usage_stats_YYYY-MM-DD.csv` and `nanda_usage_timeseries_YYYY-MM-DD.csv`). They are the archive of record: months ICPSR has dropped exist nowhere else, and the history is rebuilt from them on every run.

**Scrape guardrail and quarantine.** Between the scrape and `build_history.py`, the workflow runs `check_scrape.py`, which compares the new snapshot to the previous dated one. It fails if any of these is true:

- more than 25% of studies that had a nonzero total last time now report 0 or are missing;
- the curated time-series has no rows for the most recent complete month (the calendar month before the scrape date);
- curated unique users add up to 0 when the previous scrape's sum was above 0.

An ICPSR history trim lowers totals and unique users but passes all three. When the check fails, the run moves the new dated snapshot and time-series files into `data/quarantine/<scrape-date>/`, commits and pushes only that folder, skips the history, delta, and dashboard steps (so the live dashboard keeps last month's numbers), and ends red so GitHub emails the repo owner. `build_history.py`, `generate_delta.py`, and `build_dashboard.py` read only the top level of `data/`, so quarantined files never reach the history or the dashboard. The first quarantined scrape is 2026-11-01 (see `diagnosis-2026-11-empty-scrape.md`).

To test a quarantined scrape by hand: `python check_scrape.py --stats data/quarantine/<date>/nanda_usage_stats_<date>.csv --prev-stats data/nanda_usage_stats_<previous-date>.csv`. If a quarantined scrape turns out to be valid, release it: move its files back to `data/`, then run `python build_history.py`, `python generate_delta.py`, and `python build_dashboard.py`, and commit the results.

The scraper prints a `WARN <study_id>` line for every request that ends in a non-200 response (with the status, server, and Cloudflare `cf-mitigated` header) and for every PCMS response with no monthly buckets. It retries 403, 429, 5xx, and timeouts twice, with a short wait, before giving up.

## Maintaining the inventory

`inventory.csv` is generated. Every Monday the private `nanda-inventory` repo's weekly job writes it from scratch from that repo's `deposit_status.csv`, the one place the NaNDA dataset list is kept, and pushes it here. Each row carries `study_id`, `archive` (`ICPSR` or `openICPSR`), `deposit_via` (`legacy` or `RDE`), `status` (`published` or `unpublished`), `title`, `version`, `version_date`, `doi`, and `url`. The scraper derives the list of studies to scrape from `study_id` at runtime, joins titles by ID, and routes API calls by `archive`.

Do not hand-edit `inventory.csv`: the next weekly run overwrites it. Adds, fixes, and removals all happen in `nanda-inventory/deposit_status.csv`:

- A newly published dataset enters when a curator marks it `Done!` in the NaNDA Curation Pipeline sheet. To add one outside that path, append a row to `deposit_status.csv`.
- To fix a title, version, DOI, or URL, edit the cell in `deposit_status.csv`. Versions, version dates, and DOIs also refresh weekly from the ICPSR study pages, through a run on Lindsay's computer that opens a pull request in nanda-inventory. Once the weekly job pushes the new `inventory.csv` here, the dashboard rebuilds from it on its own.
- To remove a dataset, delete its row from `deposit_status.csv`. The next export drops it here. The export refuses to run if a single week would drop more than five rows.

The `add_to_inventory.ps1` and `add_to_inventory.py` helpers that used to append rows here were retired on 2026-11-23, since they wrote to a file that is now regenerated weekly. They remain in git history.

## Running locally

GitHub Actions runs the full pipeline (scraper, download history, delta report, dashboard build) on the 1st of every month at 9 AM UTC and commits results back to the repo (`.github/workflows/monthly-scrape.yml`). A second workflow (`.github/workflows/build-dashboard.yml`) runs only `build_dashboard.py` and commits `docs/index.html` whenever `inventory.csv` changes on `main`; it never scrapes and never writes under `data/`. Manual runs of either happen from the **Actions** tab.

To run locally:

```bash
cd usage-metrics
pip install -r requirements.txt
python nanda_usage_scraper.py     # ~5 min for 104 studies (1-second polite delay, two requests per self-published dataset)
python build_history.py           # writes data/nanda_download_history.csv
python generate_delta.py          # writes data/delta_*.md
python build_dashboard.py         # writes docs/index.html
```

To publish the dashboard, enable GitHub Pages: **Settings → Pages → Source: Deploy from a branch → Branch: `main` / folder: `/docs`**. Pages only allows publishing from `/` or `/docs`, which is why the file lives in `docs/`.

## Limitations

- **No per-institution download counts.** PCMS's `/institution` endpoint returns institution metadata (name, location, type) but no download counts per institution. We expose `num_institutions` but not a top-institutions list.
- **openICPSR has no documentation/data split.** The openICPSR usage endpoint returns one `totalDownloads` figure with no breakdown.
- **No geographic breakdown.** PCMS does not expose a country/region/state download breakdown for studies. Verified by probing every plausible endpoint and inspecting the dashboard JS bundles; no such widget exists in the public utilization page.
- **Self-deposit (RDE) counts are GA4-only.** The usage-statistics endpoint of ICPSR's self-deposit system only captures activity since GA4 tracking went live there. For self-published datasets the scraper adds the earlier version's openICPSR count to it, so their totals include both periods, but the two parts may overlap by a small number of downloads. A curated study routed by `deposit_via=RDE` gets the GA4 number alone, which is much smaller than its PCMS history (curated 38528 shows thousands of lifetime downloads in PCMS but about a hundred on the GA4 endpoint); don't compare such a row to a legacy curated row without that caveat. The GA4 endpoint also returns 500 for very new studies until ingestion catches up (logged in `error_message`; the prior value is kept for openICPSR rows, counts stay at 0 for curated RDE rows).
- **Self-published and RDE rows have no per-month time-series, publications, or institutions.** Neither the openICPSR usage endpoint nor the usage-statistics endpoint exposes monthly buckets, so these rows are excluded from `nanda_usage_timeseries_*.csv` and leave `publications`, `unique_users`, and `num_institutions` blank. Views come from the openICPSR endpoint only, so curated RDE rows have none.

## Notes

**Date window: read before comparing to the PCMS page.** The scraper still asks PCMS for everything since `01/01/2020`, but ICPSR keeps only a rolling three-year window of download history and periodically removes older months, whatever the request asks for. So ICPSR-reported totals (`total_downloads` in the snapshot CSVs and the delta report) now roughly match the default three-year view on the public utilization page at `pcms.icpsr.umich.edu/pcms/metrics/studies/{id}/utilization`. They can run slightly higher, because ICPSR trims in batches rather than monthly, so between trims its window reaches back a little more than three years. To see the same window the scraper gets, set the page's Start Date to `01/01/2020` and click **Go**. The dashboard's curated totals run higher than both, by the downloads preserved in `nanda_download_history.csv` from months ICPSR no longer reports.

**Cloudflare on GHA.** GitHub Actions sometimes runs from IP ranges Cloudflare treats as bot traffic. If a monthly run fails with a Cloudflare challenge, fall back to running `python nanda_usage_scraper.py` locally and committing the results manually.

**Diagnostic scripts.** Probe scripts in `debug/` (kept local, not pushed) help locate new endpoints if ICPSR changes its page structure or API.
